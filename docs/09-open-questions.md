# 09 — Open questions

Claims below are plausible from docs but unverified. Each gets a smoke test in its phase; record the result here and only then let the README state it as fact.

| ID | Question | Phase | How to verify | Result |
|---|---|---|---|---|
| Q1 | How is dual format (ICEBERG + DELTA) expressed in the CLI, REST API, and Terraform provider? CLI doc says "one of". | 5 | Try Terraform `table_formats = ["ICEBERG","DELTA"]`; fall back to REST `PATCH`/`POST` with array; then CLI. Record which worked and the provider version. | **Terraform works.** `confluent_tableflow_topic` with `table_formats = ["ICEBERG", "DELTA"]` on provider 2.86.0 created the topic; `confluent tableflow topic describe` shows `"table_formats": "DELTAICEBERG"` and phase `RUNNING`. CLI v4.37.0 `--table-formats` is still a single string ("one of DELTA or ICEBERG") and has no error-handling flag, so it was not used. REST not needed. |
| Q2 | Exact argument names for `confluent_tableflow_topic`, `confluent_catalog_integration`, `confluent_provider_integration` at the pinned provider version. | 2, 5 | Registry docs page for the pinned version; `terraform validate`. | **Provider 2.86.0.** `confluent_provider_integration`: `display_name`, `environment{id}`, `aws{customer_role_arn}`; exports `aws[0].iam_role_arn`, `aws[0].external_id` (applied Phase 2). `confluent_tableflow_topic`: `byob_aws{bucket_name, provider_integration_id}` (not `byos_aws`), `table_formats` list of `ICEBERG`/`DELTA`, `retention_ms`, `error_handling{mode, log_target}`, `credentials{key,secret}` = Tableflow API key. `confluent_catalog_integration`: `aws_glue{provider_integration_id}`, `credentials`. Source: provider repo `docs/resources` at tag v2.86.0. Apply-time verification of the last two in Phase 5. |
| Q3 | What Glue table name does Tableflow produce for topic `orders.clean` (dot in name)? | 5 | `aws glue get-tables --database-name <cluster-id>` | `orders.clean`, dot kept. Database `lkc-q2zqngd`, `TableType EXTERNAL_TABLE`, parameters `table_type=iceberg`, `metadata_location`, `current_snapshot_id`. Columns = topic columns + `$$topic`, `$$partition`, `$$headers`, `$$leader-epoch`, `$$offset`, `$$timestamp`, `$$timestamp-type`, `$$raw-key`, `$$raw-value`. PyIceberg loads it with the tuple identifier `("lkc-q2zqngd", "orders.clean")`; Athena needs `"lkc-q2zqngd"."orders.clean"`. |
| Q4 | S3 layout for a dual-format topic: are Parquet data files shared between Iceberg and Delta or duplicated? Where is the Delta root path? | 5 | `aws s3 ls --recursive` after two commits; compare data file counts referenced by Iceberg manifest vs `_delta_log`. | **Shared.** One root = `table_path` = `s3://tableflow-demo-lake-706193894984/1100000/11101001/cfd75085-a017-4113-81ff-f34b6f2d2a87/env-876zz7/lkc-q2zqngd/v1/5839772c-c3b9-46e6-8dea-137d2269d7af` with `data/`, `metadata/` (Iceberg), `_delta_log/` (Delta). After the first commits the 6 `data/*.parquet` files in S3 are exactly the 6 `add` paths in `_delta_log` and the 6 data files of the current Iceberg snapshot (20,505 records). The Delta root is `table_path` itself (`_delta_log/` directly under it); Delta uses column mapping mode `id`. Layout detail in docs/05. |
| Q5 | Does a Flink-created sink table with `PRIMARY KEY ... NOT ENFORCED` and `changelog.mode='append'` produce a key schema Tableflow accepts? | 4–5 | Enable Tableflow on `orders.clean`; check status. | **Phase 4:** the DDL registered `orders.clean-key` (Avro record with `order_id`) and `orders.clean-value`; `SHOW CREATE TABLE` reports `changelog.mode = 'append'`, `key.format`/`value.format = 'avro-registry'`. **Phase 5:** Tableflow enabled on that topic reached `RUNNING` with both formats; the key schema was accepted. Remember `value.fields-include = 'all'` (docs/04) or the key column is absent from the table. |
| Q6 | Avro `decimal` logical type mapping through Tableflow to both formats. | 3 | Only if a decimal column is added; otherwise keep `long` cents. | Skipped by design: `unit_price_cents` is a `long`. | Q7 | Does the `LOG` error-handling strategy exist in the pinned Terraform provider? | 5 | Registry docs; else use `SKIP` and note it. | Docs for 2.86.0: `error_handling.mode` accepts `SUSPEND`, `SKIP`, `LOG` (default `SUSPEND`); `log_target` names the DLQ topic. **Confirmed at apply:** `mode = "LOG"`, `log_target = "orders_tableflow_errors"` accepted; `describe` shows `record_failure_strategy: LOG`. Two constraints found: the target name may not contain periods (`400 ... Periods are not allowed`), and the enabling account (owner of the Tableflow API key) needs write on the DLQ topic or the topic fails with "unable to set up the DLQ topic". |
| Q8 | Minimum IAM verbs for `tableflow-writer` per the current BYOS quick start. | 1–2 | Copy from the Confluent-generated policy in the Console during PI setup; diff against 02. | **S3 (Phase 1):** from [Configure Storage](https://docs.confluent.io/cloud/current/topics/tableflow/how-to-guides/configure-storage.html): bucket `s3:GetBucketLocation`, `s3:ListBucketMultipartUploads`, `s3:ListBucket`; objects `s3:PutObject`, `s3:PutObjectTagging`, `s3:GetObject`, `s3:DeleteObject`, `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts`. Three more than 02 listed (`PutObjectTagging`, `ListBucketMultipartUploads`, `ListMultipartUploadParts`); implemented in `terraform/aws/iam-writer.tf`. **Glue:** not published in docs ([Glue integration page](https://docs.confluent.io/cloud/current/topics/tableflow/how-to-guides/catalog-integration/integrate-with-aws-glue-catalog.html) shows only the Lake Formation variant); the Console generates the template. Using the 02 superset. **Phase 5:** the Glue catalog integration reached `CONNECTED` and created the database and table with that policy (`CreateDatabase`, `GetDatabase(s)`, `CreateTable`, `GetTable(s)`, `UpdateTable`, `DeleteTable` on catalog + `database/lkc-q2zqngd` + `table/lkc-q2zqngd/*`). The Console template was not retrieved (no UI session in this run), so this is "sufficient", not "minimal". |

| Q10 | Databricks path-based read of a Tableflow Delta table (no Unity integration). The catalog doc says Delta tables are "available only through Unity Catalog integration"; the overview and the private-network workaround imply path reads work. | 6 | `CREATE TABLE ... USING DELTA LOCATION` in any workspace, or delta-rs as proxy. | **Path reads work** with the reference reader: Spark 3.5 + Delta Lake 3.3 (`spark.read.format("delta").load(table_path)`) reads the table (version 10, 23,249 rows at the time). No Databricks workspace was available, so `consumers/delta/databricks.sql` is written but not executed; Databricks Runtime ships the same Delta reader features, so the path read is expected to work there too. delta-rs is *not* a valid proxy (Q11). |
| Q11 | Which open-source Delta readers can read Tableflow's Delta output? | 6 | Try delta-rs, DuckDB, Spark against `table_path`. | Tableflow's log sets `minReaderVersion 3` with reader features `typeWidening`, `deletionVectors`, `columnMapping` (mode `id`, physical names `col_N`, Parquet files carry logical names + field IDs). **Spark 3.5.7 + delta-spark 3.3.2: works** (read, count, version). **deltalake 1.6.5 (delta-rs, latest release as of 2026-09-23): refuses.** pyarrow path: `DeltaProtocolError: The table has set these reader features: {'deletionVectors', 'typeWidening', 'columnMapping'} but these are not yet supported by the deltalake reader.` DataFusion `QueryBuilder` path: `DeltaError: External error: Transaction failed: Unsupported table features required: [TypeWidening]`. The 1.6.x release notes add column-mapping and deletion-vector work but no type-widening read support, so there was no newer version to retest. **DuckDB 1.5.5 (delta ext `45c4087`) and 2.0.0.dev2609221243 (delta ext `d1b2ffd7de`): `count(*)` correct, every column NULL** because the Delta schema maps to physical names `col_N` while the Parquet files carry logical names with `PARQUET:field_id`; DuckDB resolves by physical name. Confluent's Tableflow docs (overview, Delta quick start, Delta/Unity GA post) do not state the protocol version or table features written; the list above is observed from `_delta_log/00000000000000000001.json`. Consequence: the Delta consumer is Spark-based; the runner bundles jars + a JDK. |
